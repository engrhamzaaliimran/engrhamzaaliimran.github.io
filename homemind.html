HomeMind / an agentic smart-home assistant

Building a local, small-model assistant that translates natural-language requests into safe, verifiable simulated smart-home actions. Stage 02.1 improved tool execution through Python validation; Stage 02.2 tested execution-honesty prompting. The latest Stage 02.3 pairs a Qwen3-1.7B agent with an independent Qwen3-0.6B claim verifier and benchmarks the results against 100 scenarios.

Larger does not always mean better: the 1.7B configuration outperformed the tested 4B run, although the 4B output limit was a major confound. See model benchmarks →

Stage 02.2 · Prompt engineering experiment

Execution-honesty safeguards: limited safety gains

Method and source ↗

Adding rules to verify claims, refuse unsupported operations, avoid fictitious success reports and reject contradictory requests reduced unrequested device-state changes from 4/100 (Stage 02.1) to 1/100 (Stage 02.2 prompt only). Expected action sequences stayed at 33/35.

33 / 35Verified action sequences · unchanged
99 / 100No unrequested changes · prompt only
98 / 100No unrequested changes · with explicit tool descriptions

The separate explicit tool-description experiment did not improve verified actions or eliminate false success claims; it added one unauthorized change compared with the prompt-only run. HM092–HM094 still claimed actions had succeeded without real execution. Stage 02.2 prompt-only qualitative review: 73 full passes / 16 partial / 11 failures. The separate tool-description variant has deterministic results only.

How the agent was evaluated

A repeatable experiment that tests what HomeMind actually did, not only what it said.

Stage 02 implementation

Qwen3-1.7B via Ollama and LangChain create_agent() with four structured tools: get_home_state, set_temperature, set_light and set_door_lock. The agent includes a one-shot example and an intent → capability → execution-verification → response procedure; Stage 02.2 adds evidence-first honesty safeguards.

It stores simulated device state in JSON; only the latest five user turns are held in RAM. Device-state persistence is not conversational memory.

Runner checks + GPT-6 judgments

The runner loads the selected Stage 02/02.1/02.2 agent initialization, uses isolated state per scenario, sends 120 requests across 100 tests and records structured tool calls, results and state changes. For Stage 02.1 and 02.2, verified actions are checked after deterministic ID correction.

  • Python: exact tool/argument matches, successful writes, final state and unexpected changes.
  • GPT-6: user intent, response honesty, ambiguity, general-knowledge correctness and qualitative scenario verdicts.

Stage 01 context

In the original prompt-only experiments, Qwen sometimes claimed to control devices with no tools. A capability-first prompt refused three consecutive action-related requests in one exploratory run (3/3)—not a validated accuracy figure.

Stage 02 introduced real tool calling and an illustrative one-shot example. The prompt evolved in several ways, so the manual experiments do not isolate the effect of one-shot prompting.

Stage 01 experimental log ↗

Interpretation limits: These are single runs on a fixed, deliberately challenging simulated-device benchmark. It is not a production reliability estimate or a controlled experiment proving that one-shot prompting caused the observed behavior. Some context tests had failed earlier setup actions, which should not be counted automatically as standalone memory failures.

Stage 01 and early Stage 02 experiments

The current benchmark builds on earlier manual observations. These records remain part of the project rather than being replaced by the new evaluation dashboard.

Stage 02 — Why we introduced one-shot prompting

Early tool-enabled prompts did not consistently yield real structured calls. In some sessions the model printed a tool name or a JSON-like function call as plain text, refused available home-state queries, or copied a response placeholder. We introduced one concrete example mapping "Turn on the bedroom light" to set_light(room="bedroom", on=True) and explicitly instructed Qwen to use the registered tool interface.

Manual experimentObserved outcome
Earlier prompt: "what is temperature of bedroom"Printed get_home_state as text; no execution evidence
Earlier prompt: "change it to 21"Printed a function-call-like object; no verified execution
Revised one-shot prompt: read state and change living-room targetReal get_home_state and set_temperature tool calls with results
Revised prompt: general knowledge, recent follow-up, unsupported deviceAnswered, recalled setpoint and refused one unsupported request in a manual session

These runs were informal and included other prompt changes; they cannot establish a causal improvement from the one-shot example alone. Read the Stage 02 notes ↗

Stage 01 — Prompt-only capability and hallucination tests

The original Qwen baseline could recall user context yet sometimes claimed to change device state despite having no tools. A mandatory intent → capability check → execution verification → response procedure improved observed refusals (3/3 in one small exploratory run).
