HomeMind / an agentic smart-home assistant

Building a local, small-model assistant that translates natural-language requests into safe, verifiable simulated smart-home actions. The project develops from baseline LLM inference and prompt engineering to tool use, stateful orchestration, and controlled fine-tuning.

Project target and current capabilities

The target

A simulated smart-home environment in which an LLM interprets commands, selects appropriate tools, executes multi-step routines, verifies outcomes, and reports actions based on actual device state—not invented completion messages.

  • Natural-language device control and follow-up commands
  • Tool calling with structured arguments
  • Stateful workflows, confirmations and recovery
  • Model evaluation and LoRA adaptation

What's working today

Local Qwen3-1.7B inference, message-history management and iterative system prompts. The baseline can recall a revised temperature request and interpret multi-action language. Stage 01 established a capability-first prompt (3/3 observed probes). Stage 02 now uses LangChain create_agent() with four real Python tools and persistent JSON state. Manual tests confirmed genuine tool calls, successful state updates, and correct rejection of an unknown light.

  • Simulated device control is implemented; no physical devices connected
  • Conversation history is RAM-only; persistence, context selection and recall validation are pending
  • 100-scenario evaluation, advanced workflows and fine-tuning remain pending

Completed investigation · 11 October 2026

Stage 01 — From false execution claims to capability-first prompting

The initial model understood requests but would say it had set the thermostat despite having no tools. General prohibitions and an explicit empty tool list did not reliably prevent this. A mandatory capability-check sequence improved the observed responses.

The prompt-engineering change

01 / INTENTInterpret request

Identify desired action and follow-up context.

02 / CAPABILITYMatch available tool

No matching tool → unavailable.

03 / EVIDENCEVerify execution

A tool result, not a prior message, proves success.

04 / RESPONSEReport status

State what can and cannot actually be done.

BEFORE / UNSUPPORTED CLAIM
“I have set your bedroom thermostat to 21°C.”
AFTER / CAPABILITY-FIRST
“Capability: UNAVAILABLE. I cannot directly set the thermostat…”
See the capability-first prompt procedure
SYSTEM CAPABILITIES:
Available tools: []
Verified execution results: []

MANDATORY DECISION PROCEDURE:
1. INTENT — Interpret the user's request, including context.
2. CAPABILITY CHECK — Find a matching available tool.
   If absent, mark UNAVAILABLE; do not promise execution.
3. EXECUTION VERIFICATION — Completion requires a matching,
   successful tool result; conversation is not evidence.
4. RESPONSE — Report capability and actual status.

Format:
Capability: AVAILABLE or UNAVAILABLE
Response: [explanation]
Experimental scope: 3/3 refers to one manually observed session, not a statistically validated accuracy rate. The debug run independently confirmed the previous prompt and empty tool lists were delivered. Earlier assistant responses may have reinforced unsupported claims, but causation was not isolated. General role-description wording remained ambiguous. Real execution must be enforced by application code in later stages.
